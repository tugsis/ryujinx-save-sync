# Yuzu 동기화 지원 추가 기획

- 작성일: 2026-10-21
- 기준: RyuSync `v0.1.0-alpha.1`, 커밋 `dd5661a`
- 상태: 추가 구현 제안. 이 문서를 작성한 시점의 배포판은 Ryujinx만 지원한다.
- 대상: Windows 11 x64, SteamOS/Linux x64의 사용자가 보유한 Yuzu 설치본
- 기존 기획: [PLAN.md](../PLAN.md)

## 1. 목표와 권장 방향

기존 WebDAV 전송·스냅샷·이력·충돌 처리 엔진을 재사용하고, 에뮬레이터별 탐색·세이브 읽기·적용·실행을 어댑터로 분리한다. 게임마다 세이브 폴더를 수동 지정하는 대신 **설치본의 데이터/NAND 루트를 한 번 지정하면 게임과 프로필을 자동 탐색**한다.

다음 세 가지 사용을 지원한다.

| 구성 | 동작 |
|---|---|
| Windows Yuzu ↔ SteamOS Yuzu | 같은 게임·연결 슬롯의 세이브를 서버를 통해 교환 |
| Windows Ryujinx ↔ SteamOS Yuzu | 게임의 실제 세이브 호환성을 확인한 뒤 공통 슬롯으로 교환 |
| 같은 PC의 Ryujinx + Yuzu | 두 로컬 연결을 같은 슬롯에 등록하고 순차 동기화. 처음부터 폴더를 공유하거나 서로의 폴더를 직접 덮어쓰지 않음 |

세이브 파일의 게임별 포맷을 변환하는 기능은 포함하지 않는다. **같은 Title ID는 연결 후보를 찾는 조건이며, 세이브 호환성을 보장하지 않는다.** 게임 업데이트·DLC·모드·에뮬레이터 빌드 차이와 게임의 사용자 식별 방식은 별도로 검증한다.

## 2. 지원 범위

첫 구현은 실제 검증한 Yuzu 빌드의 Account/User Save와 Windows 네이티브·Linux 직접 실행/AppImage를 대상으로 한다. 설치본 정보에 빌드 식별값과 확인한 레이아웃을 기록한다.

다음은 초기 범위에서 제외한다.

- Device Save, System Save, 캐시 세이브, 임시 저장소.
- 전체 NAND, 펌웨어, 키, 모드, 셰이더, 에뮬레이터 설정·프로필 DB 동기화.
- Android 및 Yuzu 계열 포크의 일괄 지원. 비슷한 폴더 구조만으로 지원 대상으로 인정하지 않는다.
- 게임별 세이브 포맷 변환 및 게임 세이브 내부의 계정 ID 수정.
- Flatpak/외부 실행기의 실제 프로세스 종료 추적이 검증되지 않은 구성. 경로 탐색과 실행 지원을 구분한다.

Google Drive 추가는 별도 작업이다. Yuzu 지원을 위해 WebDAV 서버나 NAS 구성을 변경할 필요는 없다.

## 3. 확인한 구조와 추가 확인 사항

### Yuzu 세이브 경로

보존된 Yuzu 소스의 특정 스냅샷에서 다음 경로 구성과 `.yuzu_save_size` 관리 파일을 확인할 수 있다. 이 자료는 현재 사용자의 설치본과 동일한 빌드라는 뜻은 아니다. 실제 빌드의 복제 세이브와 대조한 뒤 탐색 규칙을 확정한다. [Yuzu 원본 소스 보존본: savedata_factory.cpp](https://source.hodakov.me/hdkv/yuzu/src/commit/47f786ad975b991144216e4a5707b046bdf54714/src/core/file_sys/savedata_factory.cpp)

기본 탐색 대상으로 삼을 Account Save 형태:

```text
<NAND 루트>/user/save/0000000000000000/<사용자 ID>/<Title ID>/
    <게임 세이브 파일·하위 폴더>
    .yuzu_save_size  # 존재할 수 있는 로컬 관리 파일
```

같은 소스에는 `user/save/account/<사용자 ID>/<Title ID>/1` 형태를 확인하는 분기도 있다. 모든 Yuzu가 이를 사용한다고 단정하지 않는다. 초기에는 검증된 기본 레이아웃만 쓰기 지원하고, 그 밖의 레이아웃 또는 중복 후보는 경고·보류한다. 경로의 마지막 `1`만 보고 Ryujinx와 동일한 구조로 취급하지 않는다.

### 데이터 루트 후보

| 환경 | 자동 탐색 후보 및 처리 |
|---|---|
| Windows | `%APPDATA%/yuzu`, 사용자가 선택한 실행 파일 옆의 `user` 폴더를 후보로 검사. 실제 NAND 위치 확인 필요 |
| Linux | `$XDG_DATA_HOME/yuzu` 또는 `~/.local/share/yuzu`를 후보로 검사 |
| SteamOS/EmuDeck | 사용자가 선택한 Emulation 루트 아래 `storage/yuzu/nand`와 `saves/yuzu` 연결을 검사 |
| Portable·커스텀 NAND | 데이터 루트·NAND 루트를 한 번 지정하고, 설치본 설정을 읽을 수 있으면 후보를 제안 |
| Flatpak | 실제 설치된 앱 ID와 sandbox 데이터 위치에서 후보를 찾되, 초기 자동 실행 지원과 분리 |

EmuDeck 문서는 Yuzu 저장소와 세이브 링크를 별도로 설명한다. 설치마다 SSD/SD카드 경로가 다를 수 있으므로 `/home/deck/Emulation`을 고정하지 않는다. [EmuDeck 파일 관리 문서](https://github.com/EmuDeck/emudeck.github.io/blob/main/docs/file-management/steamos/file-management.md#yuzu)

경로는 확정값이 아니라 후보다. 폴더가 존재해도 세이브 구조와 설치본의 실제 설정을 확인한다. 데이터 루트에 도달하는 심볼릭 링크는 명시적으로 해석할 수 있지만, 세이브 내부 링크·경로 탈출·겹치는 대상은 거부한다.

## 4. 현재 코드에서 바꿀 부분

| 현재 파일·동작 | 필요한 변경 |
|---|---|
| `Models.cs`: 설정에 데이터 루트·실행 파일이 각각 하나 | 여러 `EmulatorInstallation`과 `LaunchProfile`로 분리 |
| `Discovery.cs`: Ryujinx 인덱스 및 `0`/`1` 경로 | `RyujinxAdapter`로 이전하고 `YuzuAdapter`를 추가 |
| `Snapshots.cs`: `Discovery.ContentPath` 호출, SaveRoot 안의 콘텐츠 하위 폴더 교체 | 어댑터가 스냅샷 대상과 적용 계획을 제공. Yuzu의 타이틀 폴더 자체가 콘텐츠인 경우 처리 |
| `Coordinator.cs`: 등록·재탐색과 같은 RemoteKey의 중복 등록 제한 | 설치본별 로컬 연결과 공통 동기화 그룹을 분리 |
| `SyncEngine.cs`: Ryujinx 전용 경로·프로세스 검사 | 논리 세이브 트리를 비교하고 설치본/그룹에 대한 실행 잠금을 적용 |
| `Storage.cs`: 원격 revision 발행·조회 | 공통 페이로드와 출처 정보를 관리하고 기존 클라이언트와 저장 영역 분리 |
| `StateDatabase.cs`: JSON 레코드 저장 | 버전 있는 가져오기·검증·복구와 설치본별 baseline 관리 |
| API·CLI·React | 설치본 선택, 연결 슬롯 매핑, 호환성 승인, 실행 프로필별 Steam 안내 |

경로 탐색기만 추가하면 다운로드 교체, 백업, 실행 중 보호가 여전히 Ryujinx 전용으로 남는다. 위 호출부를 함께 바꾸는 것이 필수다.

## 5. 백엔드 설계

### 에뮬레이터 어댑터

개념 인터페이스는 다음 책임을 가진다. 실제 함수명은 구현 과정에서 정한다.

```text
IEmulatorAdapter
  FindInstallations()             데이터·NAND·실행 파일 후보
  Scan(installation)             게임·사용자·세이브 종류·레이아웃 탐색
  Resolve(binding)               재탐색을 통해 유효한 현재 경로 확인
  ExportPayload(binding)         공통 게임 세이브 트리 생성
  PlanApply(binding, payload)    로컬 관리 파일을 보존하는 적용 계획
  BuildLaunch(profile)           셸을 사용하지 않는 구조화된 실행 정보
  InspectRunning(installation)   실행 중 / 종료 / 확인 불가
```

공통 엔진은 해시, 전송, revision DAG, baseline, 충돌 선택과 파일 검증을 담당한다. 어댑터는 세이브 구조와 로컬 메타데이터 정책을 담당한다. NAS에는 별도 RyuSync 서버를 설치하지 않는다.

### 식별 모델

| 모델 | 핵심 필드 |
|---|---|
| 설치본 | `InstallationId`, `EmulatorKind`, 빌드, 데이터/NAND 루트, 실행 방식, 실행 파일·인수 |
| 로컬 연결 | `BindingId`, `InstallationId`, `TitleId`, 로컬 사용자 ID, 세이브 종류·레이아웃, 로컬 경로, `GroupId` |
| 공통 그룹 | 정규화한 16자리 `TitleId`, 사용자 지정 `Slot`, 저장소 범위, 호환성 승인 상태 |
| 실행 프로필 | `LaunchProfileId`, 설치본, 동기화 대상 그룹, 선택적 게임 인수 |
| revision | 기존 불변 revision 정보 + 선택적 출처 에뮬레이터/빌드·게임 버전·페이로드 정책 버전 |

원격의 논리 키는 기존처럼 **Title ID + Slot**을 기준으로 한다. 에뮬레이터 종류나 로컬 UUID를 원격 키에 넣으면 Ryujinx↔Yuzu 연결이 분리되므로 포함하지 않는다. 반대로 로컬 `BindingId`에는 설치본과 세이브 종류까지 포함해 같은 게임의 서로 다른 설치본을 구분한다.

Ryujinx UUID와 Yuzu UUID는 같다고 가정하지 않는다. 이름이 같더라도 자동 확정하지 않고 사용자가 처음 한 번 같은 슬롯에 연결하도록 한다. 폴더 이름의 ID와 사용자 표시명을 구분하고, 프로필 DB의 바이트 순서·문자열 변환이 검증되지 않으면 ID를 그대로 표시한다. 프로필 DB는 읽기만 하며 자동 생성·수정하지 않는다.

## 6. 게임 이름과 세이브 자동 탐색

1. 설치본마다 데이터/NAND 루트를 확인한다. 가능한 경우 에뮬레이터의 커스텀 경로 설정을 읽기만 한다.
2. 검증된 레이아웃에서 사용자 ID·Title ID·세이브 종류를 파싱한다. ID 형식, 경로 경계, 중복·모호한 후보를 검사한다.
3. 게임 이름은 이미 등록한 동일 Title ID의 로컬 이름, 읽을 수 있는 에뮬레이터 메타데이터 또는 사용자가 선택한 게임 목록 메타데이터로 보완한다.
4. 이름을 얻지 못해도 Title ID로 등록·동기화할 수 있다. 잘못된 게임명을 추정해 자동 연결하지 않는다.
5. 동일 Title ID가 서버에 있으면 연결 후보를 제안하고 로컬 사용자와 슬롯을 확인받는다.

세이브 폴더만으로 게임 이름을 항상 얻을 수 있다고 약속하지 않는다. 이름 표시를 위해 게임 덤프의 키·펌웨어 업로드를 요구하지 않는다. 온라인 Title DB 도입은 출처·라이선스·캐시 정책을 정하는 별도 선택 기능이다.

## 7. 공통 페이로드와 안전한 다운로드 적용

서버에는 경로 래퍼와 프로필 ID를 제외한 **게임 세이브의 상대 파일 트리**를 저장한다. 파일명·바이트를 임의 변환하지 않으며 게임 내부 계정 정보도 수정하지 않는다.

| 구분 | 처리 |
|---|---|
| Ryujinx | 검증한 활성 콘텐츠 디렉터리만 공통 페이로드로 내보내기. 기존 세이브 루트의 관리 구조는 로컬 유지 |
| Yuzu | 검증된 타이틀 콘텐츠에서 `.yuzu_save_size` 등 확인된 에뮬레이터 관리 항목만 제외 |
| 백업 | 공통 페이로드와 별개로 관리 파일을 포함한 기존 로컬 대상 전체를 보존 |
| 적용 | 대상 어댑터가 콘텐츠와 관리 파일을 결합한 스테이징 디렉터리를 생성한 뒤 검증·교체 |

관리 파일 제외 규칙은 검증한 레이아웃의 정확한 상대 경로에만 적용한다. 숨김 파일 전체를 제외하거나, 모든 하위 폴더의 같은 이름을 무조건 제거하지 않는다. 관리 파일만 달라졌을 때 공통 세이브 해시가 바뀌지 않아야 한다.

Yuzu에서 받아 Ryujinx로 적용할 때 Yuzu 관리 파일을 전송하지 않는다. Ryujinx에서 받아 Yuzu로 적용할 때 기존 Yuzu 관리 파일을 보존한다. 필요한 로컬 관리 정보가 없거나 게임 요구 크기가 불명확하면 임의의 값으로 만들지 않고 초기화 필요로 보류한다.

현재 `Snapshots.Apply`는 콘텐츠가 세이브 루트의 하위 폴더라고 가정하므로 Yuzu에 그대로 사용할 수 없다. 적용 계획은 `ReplaceRoot`, `PayloadRelativePath`, 보존할 관리 항목을 명시해야 한다. 스테이징과 이전 폴더는 대상과 같은 파일시스템에 두고, 덮어쓰기 직전에 프로세스 상태와 기존 해시를 재확인한다. Yuzu 콘텐츠를 `TitleID/TitleID`처럼 중첩시키지 않는다.

ZIP 검증·크기 제한·링크 거부·원자적 디렉터리 교체·저널 복구는 기존 규칙을 유지하고 두 어댑터에서 모두 검증한다.

## 8. 최초 연결·빈 세이브·호환성

| 상황 | 동작 |
|---|---|
| 양쪽에 세이브가 있고 논리 해시가 같음 | 연결 확인 후 baseline 설정 |
| 양쪽에 서로 다른 진행 상황이 있음 | 둘 다 보존하고 최초 원본 선택. 수정 시각으로 자동 결정하지 않음 |
| 서버에만 있고 로컬 세이브가 없음 | `initialization-required` 표시. 대상 에뮬레이터에서 해당 프로필로 게임을 한 번 실행·저장·종료하도록 안내 |
| 초기화 때문에 새 세이브가 생김 | 사용자가 서버 복원을 예약한 상태를 유지하고 새 초기 세이브의 자동 업로드를 차단. 백업 후 서버 적용 |
| 프로필이 여러 개이거나 사용자 식별 불확실 | 슬롯 연결을 확인할 때까지 동기화 보류 |
| 처음 Ryujinx↔Yuzu로 연결 | 호환성 미확인 표시, 양쪽 백업과 사용자의 시험 적용 승인 후 진행 |
| 테스트에서 게임이 읽지 못함 | 성공 상태로 확정하지 않고 롤백·연결 분리 안내. 기존 revision 유지 |

초기화 실행은 일반 `launch`의 동기화와 구분한 상태로 관리한다. 필요한 경우 설치본을 수동 실행하도록 안내하고, 실제 게임 종료와 안정화가 확인되기 전에는 예약된 다운로드를 실행하지 않는다.

호환성 확인은 `미확인 → 시험 적용 → 사용자가 로드·저장 확인 → 확인됨` 흐름으로 기록한다. 해시 일치나 파일 적용 성공만으로 게임 로드 성공을 판단하지 않는다. 확인 결과는 게임 버전·에뮬레이터 빌드·사용자 조합에 연결하며, 중요한 조건 변경 시 재확인을 요청한다.

## 9. Steam 시작 전·종료 후와 웹 동기화

실행 프로필별로 `ryusync launch --launch-profile <id>`를 제공한다. 기존 `launch`는 가져온 기본 Ryujinx 실행 프로필로 연결해 사용법을 유지한다.

```text
Steam → 실행 프로필 선택 → 대상 그룹별 동기화
      → 충돌·초기화·호환성 문제 해결
      → 선택한 Ryujinx 또는 Yuzu 실행
      → 실제 프로세스 종료 및 세이브 안정화 확인
      → 변경된 로컬 연결의 종료 후 동기화
```

- 초기 구현은 하나의 백엔드에서 실행 세션을 하나씩 허용한다. 동일 그룹에 속한 두 에뮬레이터의 동시 실행을 허용하지 않는다.
- 프로세스 이름뿐 아니라 실행 경로·PID·시작 시각·설치본을 확인한다. 외부에서 수동 실행한 에뮬레이터도 보호 대상이다. 설치본 판별이 어려우면 해당 에뮬레이터 관련 그룹을 보수적으로 보류한다.
- AppImage 실행기의 부모 프로세스가 끝나도 실제 에뮬레이터가 남으면 종료 후 동기화를 시작하지 않는다. Flatpak은 앱 ID 및 실제 인스턴스 생존 추적이 검증될 때 실행 지원한다.
- 같은 슬롯에 로컬 연결이 여러 개 있으면 각 baseline으로 순차 처리한다. 둘 다 독립 변경됐으면 충돌로 중단하고 선택되지 않은 진행 상황도 보존한다. 두 대상에 동시에 일괄 덮어쓰지 않는다.
- 실행 중 웹의 동기화 요청은 대상 그룹별로 대기시킨다. 종료 후 동기화와 합치되 관련 없는 다른 설치본의 실행을 시작하지 않는다.
- 실행 확인 불가, 충돌, 서버 실패 시 실행 전 동기화 성공으로 처리하지 않는다. 명시적 오프라인 실행 정책은 별도 상태로 유지한다.

## 10. 프론트엔드·API 추가 사항

설정 페이지에 다음을 추가한다.

1. **에뮬레이터 설치본:** Ryujinx/Yuzu 종류, 빌드, 데이터·NAND 루트, 경로 검사와 탐색 결과.
2. **게임 연결:** 게임명·Title ID·에뮬레이터·로컬 사용자·슬롯을 함께 표시. 같은 게임의 연결 후보를 제안하고 사용자가 승인.
3. **호환성:** 같은 에뮬레이터 / 교차 사용, 게임 버전 확인 상태, 최초 원본, 시험 복원과 로드 확인.
4. **실행 프로필:** 실행할 설치본과 동기화 범위 선택, Steam에 복사할 대상·인수 안내.
5. **작업·충돌:** revision 출처의 기기와 에뮬레이터 표시. 이전 revision의 출처가 없으면 미상으로 표시.
6. **복원:** 적용 대상 설치본과 프로필을 명시하고 관리 파일 포함 로컬 백업에서 복구.

API 제안:

```text
GET/POST/PUT /api/installations[/<id>]
POST         /api/installations/<id>/scan
GET/POST     /api/sync-groups
POST         /api/save-sets                installationId + discoveryId + groupId
POST         /api/sync-groups/<id>/compatibility
GET/POST/PUT /api/launch-profiles[/<id>]
POST         /api/launch-sessions          launchProfileId
```

기존 `/api/ryujinx/*`는 전환 기간에 Ryujinx 어댑터로 연결되는 호환 경로로 유지한다.

## 11. 기존 데이터와 릴리스 전환

현재 `v0.1.0-alpha.1`은 새 페이로드 정책·설치본 모델을 이해하지 못한다. 구버전이 Yuzu와 공유하는 슬롯을 무심코 갱신하지 않도록 **새 기능은 원격 v2 영역과 별도 로컬 상태 디렉터리로 도입**한다.

- 기존 원격 `ryusync/<workspace>/...`와 기존 Ryujinx 이력은 변경하지 않는다.
- 교차 에뮬레이터 그룹은 `ryusync-v2/<workspace>/...`를 사용한다. 저장소 Scope에는 프로토콜/페이로드 정책 버전도 포함한다.
- 신규 로컬 기본 상태 폴더는 `RyuSync-v2` / `ryusync-v2`로 분리한다. 구버전은 같은 로컬 세이브를 계속 변경할 수 있으므로 기존 Steam 바로가기와 백엔드를 중지·교체하도록 안내한다.
- 가져오기는 구버전 백엔드 종료 확인 → SQLite 백업 API로 DB 및 관련 파일 백업 → 읽기 전용 검증 → 설치본·연결·기본 실행 프로필 생성 순서로 수행한다. 실행 중인 WAL DB 파일 하나만 복사하지 않는다.
- 기존의 선택한 정상 revision을 검증하여 v2의 첫 revision으로 가져올 수 있다. 원본 Scope·revision ID를 출처로 남기되 다른 저장소의 ID를 v2 부모로 붙이지 않는다. 기존 전체 이력은 원래 영역에 읽기 전용으로 남긴다.
- baseline은 새 원격 이력이므로 자동 재사용하지 않는다. 초기 비교·원본 선택 후 새로 설정한다. 미전송 스냅샷과 미완료 적용 저널이 있으면 기존 앱에서 해결한 뒤 가져온다.
- 구버전 자동 역마이그레이션은 제공하지 않는다. 구버전으로 돌아갈 때는 백업과 기존 원격 영역을 사용하고 최초 비교를 다시 수행한다.

이 방식은 저장 공간이 추가로 필요하지만 기존 시험판의 동기화 결과와 새 정책을 섞지 않는다. 출시 전 이 정책과 원격 경로를 확정하고, 문서·API의 v2 표기는 앱의 실제 릴리스 번호와 구분한다.

## 12. 구현 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 0. 자료·실기 확인 | 사용할 Yuzu 빌드, 데이터/NAND 경로, 게임 버전, 복제 세이브 수집 | 지원 레이아웃·관리 파일·실행 방식 확정 |
| 1. Ryujinx 분리 | 기존 동작을 어댑터 뒤로 이동 | 기존 단위·HTTP/WebDAV·런처 테스트 전부 통과 |
| 2. Yuzu 읽기 전용 탐색 | 설치본·게임·프로필 탐색과 이름 fallback | 기본/커스텀/Portable·SteamOS 경로 검증, 파일 변경 없음 |
| 3. Yuzu 동기화 | 공통 페이로드, 관리 파일 보존, 백업·저널 적용 | 합성 세이브로 Yuzu↔Yuzu 왕복과 실패 복구 통과 |
| 4. 다중 연결·교차 사용 | 슬롯 매핑, baseline 분리, 호환성 승인, v2 가져오기 | Ryujinx↔Yuzu 왕복·두 로컬 연결 충돌·기존 이력 보존 검증 |
| 5. 웹·Steam | 설치본/실행 프로필 UI, 전후 동기화, 대기 작업 | Windows·SteamOS의 실제 프로세스 생존/종료 검증 |
| 6. 시험 배포 | 게임별 실기 왕복, README·릴리스 설명 | 검증표와 한계를 공개한 새 시험판 배포 |

필수 검증 시나리오:

- Ryujinx와 Yuzu에서 같은 게임·슬롯을 공유하되 로컬 사용자 UUID가 다른 경우.
- 같은 게임에 사용자 2명, 같은 PC에 설치본 2개, 같은 실제 경로의 중복 등록.
- 관리 파일만 바뀐 경우 공통 해시 불변, 대상 관리 파일 보존, 숨김 게임 파일 보존.
- 서버 전용 세이브·첫 실행 직후 초기 세이브·원본 선택 예약의 재시작 복구.
- 양쪽 오프라인 진행, 동시 업로드, 오래된 충돌 선택 거부, 원격 기준 이력 소실.
- 다운로드 손상, 디스크 공간 부족, Windows 잠금, 파일 교체 중 종료와 저널 복구.
- 내부 링크·경로 탈출·대소문자 충돌·관리 파일 경로 충돌 거부.
- Yuzu/AppImage 실제 실행 중 웹 동기화 대기, 종료 후 업로드, 충돌 시 실행 차단.
- 구버전 DB와 원격 이력을 바꾸지 않는 가져오기, 원격 v1/v2 혼용 차단.
- 실제 게임별 `Ryujinx 저장 → Yuzu 로드·진행·저장 → Ryujinx 재로드`와 반대 방향 확인. 파일 해시 테스트와 게임 로드 검증을 별도로 기록.

완료 판단은 Yuzu 폴더를 찾는 것에 그치지 않는다. 지정한 게임·버전에서 양방향 로드·저장과 실행 중 보호, 실패 복구가 확인되어야 해당 조합을 지원으로 표시한다.

## 13. 구현 전에 필요한 사용자 환경 정보

기획 작성에는 필요하지 않지만, 실제 구현·실기 검증 전에 다음을 확인한다.

- Windows/SteamOS에서 사용할 Yuzu 빌드와 실행 형태(EXE, AppImage, Flatpak 등).
- 데이터 폴더와 실제 NAND 경로, Portable·커스텀 경로 사용 여부.
- 교차 사용할 게임의 Title ID와 게임 업데이트 버전.
- Ryujinx↔Yuzu 교차 사용 여부, 같은 PC에서 두 에뮬레이터를 함께 사용할지 여부.

개인키·펌웨어·게임 원본을 수집할 필요는 없다. 테스트용 디렉터리 구조·메타데이터와 사용자가 로컬에서 검증하는 복제 세이브로 진행한다.
